# 面试准备（八股题）

> 目标：过一面/二面技术面。核心是**作答顺序**——标准答案踩分在前，工程实践案例在后。

## 一、作答原则

### 两段式模板（每题都按这个顺序）

1. **标准答案段（拿分）**：定义 / 结论 / 分类，按面试官 checklist 给全踩分点
2. **工程实践段（展示）**：1 个真实项目案例，**先铺动机再讲方案**

### 三条禁忌

1. **见解先行**：面试是单向评分，不是技术交流。观点只能后置，不能开场就否定题目价值
2. **挑战题目前提**：即使内心认为"MVC/MVVM 只是名字差异"，也要先给定义差异，再说"工程实践中边界会模糊"
3. **抛细节不铺背景**：讲超出面试官认知的方案前，先讲动机（场景/痛点），让对方顺着你的逻辑走

### 兜底话术（遇到没准备的题）

不要硬编。模板：「这块我实际用得少，从原理上理解是……（给已知部分）；但在我们项目里有个相关场景……（往熟悉方向引）」。给诚实边界 + 往自己的强项引导。

## 二、高频题清单

### 1. MVC/MVP/MVVM/MVI 区别 ★（挂过，重点准备）

**踩分点**
- MVC：Model-View-Controller。Android 早期 Activity/Fragment 身兼 View 与 Controller，职责不清、难测试
- MVP：Model-View-Presenter。Presenter 做桥梁，View 只渲染，接口隔离、可测试性好，但接口多、模板代码多
- MVVM：Model-View-ViewModel。ViewModel 持有 UI 状态，View 订阅观察，低耦合，解决 Controller 臃肿；配合 LiveData/Flow/Compose State
- MVI：Model-View-Intent。单一数据源、单向数据流、状态不可变，可预测易调试，但模板多、小场景偏重
- 区别核心：数据流向、职责划分、耦合度、可测试性

**我的项目案例**（先铺动机）
HAGO 用 MVVM，做过一处延伸：ViewModel 绑定**业务 Context** 而非页面生命周期——因为语聊房多个页面要共享同一份麦位状态，跟随 Activity 会在切页时销毁重建、状态丢失。同时沉淀了单向数据流状态管理容器，按属性分发减少冗余刷新。

**可能的追问**
- "生命周期不跟页面走有什么坑？" → 需要自己管理清理时机；我们让协程生命周期与状态管理器自动绑定，自动释放，解决泄漏
- "为什么引入单向数据流？" → 高频刷新场景状态流复杂、刷新粒度粗，单向流可预测、易排查

### 2. 常用设计模式 ★（挂过，重点准备）

**踩分点**
- 单例：饿汉 / 懒汉 / DCL（volatile）/ 静态内部类 / 枚举，注意线程安全与序列化
- 观察者：发布订阅，LiveData / Flow 本质就是观察者
- 工厂 / 抽象工厂：创建解耦
- 建造者：链式构造复杂对象，OkHttp / AlertDialog
- 适配器：接口转换，RecyclerView.Adapter
- 策略：算法族可替换
- 模板方法：骨架固定、步骤可变
- 责任链：OkHttp 拦截器链、View 事件分发
- 代理：动态代理，Retrofit 核心

**我的项目案例**
海外第三方 SDK 统一接入层：用**适配器 + 策略**把 Google/Facebook/TikTok 登录、各家广告 SDK 归一为统一接口；状态管理容器用**观察者**实现按属性分发订阅。

**可能的追问**
- "单例怎么保证线程安全？" → DCL + volatile 防止指令重排；或静态内部类延迟加载
- "观察者模式有什么问题？" → 注意内存泄漏，及时反注册；我们靠协程生命周期自动解绑

### 3. 组件化与跨模块通信

**踩分点**
- 组件化：按业务拆分独立 module，可独立编译/运行；分层（宿主 + 业务组件 + 基础库）
- 通信方案：接口下沉、服务注册发现、路由；避免业务间直接依赖，靠编译期保障
- 隔离原则：依赖倒置，业务模块间不直接引用

**我的项目案例**
主导模块化架构：基于 KSP 编译期生成服务注册与发现代码，接口与实现编译期校验，避免运行时反射开销；承载 HAGO 全部 100+ 业务模块。

**可能的追问**
- "为什么不用运行时反射？" → 性能开销 + 错误只能运行期暴露，编译期校验提前发现问题
- "和 ARouter 比？" → 同类思路；自研为和编译期校验、Service 体系整合，且不引入额外依赖

### 4. Compose vs View

**踩分点**
- View：命令式 UI，XML + 代码分离，成熟生态、性能可控，但状态同步需手动
- Compose：声明式 UI，状态驱动重组，无 XML、代码即 UI，局部智能重组；天然契合单向数据流
- 关键差异：声明式 vs 命令式、重组机制、状态管理（remember / mutableStateOf / StateFlow）

**我的项目案例**
统一 Compose 与传统 View 的状态消费 API，一套 ViewModel 在两种 UI 下行为一致，已覆盖直播间、主页、导航等核心模块。

**可能的追问**
- "Compose 怎么避免多余重组？" → 状态按属性分发、稳定类型（@Stable/@Immutable）、derivedStateOf 派生状态
- "Compose 状态存哪？" → 简单 UI 用 remember，跨页面/共享用 ViewModel + StateFlow

### 5. Kotlin 协程

**踩分点**
- 协程是轻量级并发，可挂起非阻塞；挂起函数编译为 Continuation 状态机
- 结构化并发：作用域、父子关系、取消传播、异常处理
- 调度器：Main / IO / Default / Unconfined
- 与线程区别：协程用户态调度，一个线程可跑多个协程，切换无内核开销

**我的项目案例**
状态管理框架让协程生命周期与状态管理器自动绑定，免手动管理、降低泄漏风险，跨页面/模块共享同一套 setState 规范。

**可能的追问**
- "协程为什么不会阻塞线程？" → 挂起点保存现场后线程返回干别的，恢复时再切回
- "怎么避免协程泄漏？" → 结构化并发，用明确作用域 + 自动取消

### 6. Kotlin 特性

**踩分点**
- 扩展函数：不修改类即可加功能（静态派发，不真正进类）
- sealed class：受限层级，when 可穷尽、无 else
- inline / reified：消除 lambda 对象分配 + 泛型实化
- 空安全：编译期可空性检查，边界一次收敛
- data class、高阶函数、委托

**我的项目案例**
业务框架大量用 sealed class 表达状态层级、扩展函数组织代码；默认非空类型，可空只在平台边界出现并一次收敛。

**可能的追问**
- "inline 什么时候用？" → 带 lambda 的高阶函数，避免匿名类对象 + reified 场景
- "扩展函数能访问私有成员吗？" → 不能，本质是静态方法，作用域受可见性限制

### 7. 集合源码 HashMap / ConcurrentHashMap

**踩分点**
- HashMap：数组 + 链表 + 红黑树；hash 定位，默认负载因子 0.75，扩容 2 倍；非线程安全；1.8 尾插法解决并发死循环
- ConcurrentHashMap：1.8 用 CAS + synchronized 锁单个桶，1.7 分段锁；线程安全
- Android 优化：SparseArray / ArrayMap 替代 Integer key 场景

**我的项目案例**
—

**可能的追问**
- "为什么引入红黑树？" → 哈希冲突严重时链表退化 O(n)，红黑树降为 O(logn)
- "1.7 头插法为什么死循环？" → 并发 resize 时链表成环

### 8. GC 与 JVM 内存模型

**踩分点**
- 运行时数据区：堆、虚拟机栈、方法区/元空间、程序计数器、本地方法栈
- GC 算法：标记清除、复制、标记整理、分代收集
- 判定：可达性分析 + GC Roots；引用类型（强/软/弱/虚）
- ART vs Dalvik：AOT vs JIT；Android 内存泄漏本质是长生命周期引用短生命周期

**我的项目案例**
VM 生命周期治理——绑定业务 Context 而非 Activity，避免页面销毁后状态仍被持有导致泄漏。

**可能的追问**
- "内存泄漏怎么定位？" → Profiler + LeakCanary（弱引用 + ReferenceQueue，GC 后检测）

### 9. 跨进程通信 Binder / AIDL

**踩分点**
- IPC 方式对比：Bundle / 文件 / ContentProvider / Socket / Messenger / AIDL
- Binder：一次拷贝（mmap 内核用户空间共享内存），C/S 模型，内核驱动，安全高效
- AIDL 自动生成 Stub / Proxy；Binder 线程池处理并发

**我的项目案例**
—

**可能的追问**
- "Binder 为什么只需一次拷贝？" → mmap 让内核缓冲与用户空间映射同一块物理内存
- "和 Socket 比？" → Socket 效率低、需处理协议；Binder 面向 Android 内部高频 IPC

### 10. Handler 机制

**踩分点**
- Looper / MessageQueue / Handler / Message 四要素
- 每线程一个 Looper：主线程默认有，子线程需手动 Looper.prepare / loop
- 消息入队出队、同步屏障、IdleHandler
- 延迟消息实现 + epoll 阻塞唤醒

**我的项目案例**
—

**可能的追问**
- "Handler 内存泄漏？" → 非静态内部类持有外部 Activity + 消息延迟未处理；用静态内部类 + 弱引用 + removeCallbacks
- "同步屏障是什么？" → 优先处理异步消息（如 VSYNC 驱动 UI 刷新），普通消息被暂时跳过

### 11. 启动优化

**踩分点**
- 启动阶段：Application onCreate → Activity onCreate → 首帧
- 手段：异步 / 懒加载初始化、启动器框架（DAG 拓扑排序）、多进程分担、异步 inflate、预加载
- 指标：冷启动时间、首帧时间

**我的项目案例**（先铺动机，含失败教训）
为加快房间打开速度，早期**整体复用房间 UI**，但多数业务不支持重入/幂等，收敛为**业务按需复用**——麦位等模块实现完整复用。首页沉淀为统一框架，新 App 零排期接入。

**可能的追问**
- "为什么整体复用会失败？" → 复用假设业务可重入/幂等，实际多数业务状态被污染；改为按需复用，边界清晰的模块（麦位）才做完整复用

### 12. 内存泄漏与优化

**踩分点**
- 常见泄漏：静态引用 Activity、非静态内部类/匿名类、Handler、单例持有 Context、监听器未注销、集合未清理
- 检测：LeakCanary、Profiler、MAT
- 优化：生命周期感知、弱引用、及时反注册

**我的项目案例**
ViewModel 绑定业务 Context 而非页面生命周期，从根上避免页面销毁后状态被持有；UI 复用踩过重入/幂等的坑，收敛为按需复用。

**可能的追问**
- "单例持有 Context 用什么？" → Application Context，避免持有 Activity

### 13. 卡顿 / 频繁刷新优化

**踩分点**
- 卡顿来源：主线程耗时、频繁刷新、过度绘制、频繁 GC
- 优化：增量刷新、合并刷新、请求缓存、DiffUtil、异步渲染
- 监控：BlockCanary、Looper Printer、Choreographer

**我的项目案例**
麦位高频刷新改**增量刷新 + 合并刷新 + 高频请求加缓存**；状态管理容器按属性分发而非整对象通知，减少冗余刷新。

**可能的追问**
- "增量刷新怎么做？" → 状态按属性分发，只有变化的属性触发对应订阅者刷新，而非整对象通知

### 14. 网络优化

**踩分点**
- 弱网优化：超时重试、降级、兜底域名/IP、长连接
- 连接复用、HTTP/2、Gzip、Protobuf
- DNS 优化、请求合并

**我的项目案例**
登录容错链路：SDK 异常降级 + 弱网自动重试 + 域名不可达切换备用域名/IP 兜底；Protobuf 为唯一来源自动生成双端网络代码。

**可能的追问**
- "降级触发条件与回切？" → 连续失败阈值触发降级，探测成功后再回切；需要准备具体阈值设计说辞

### 15. 性能优化总览

**踩分点**
- 维度：稳定性（崩溃/ANR）、启动、卡顿、内存、包体、电量流量
- 方法论：监控 → 定位 → 优化 → 验证闭环

**我的项目案例**
聚合第 11~14 题素材：启动（UI 复用策略）、卡顿（麦位增量刷新）、内存（VM 生命周期）、网络（弱网降级）。

**可能的追问**

### 16. Gradle 构建与 APK 瘦身

**踩分点**
- 构建优化：配置缓存、并行编译、增量构建、Kotlin DSL、依赖优化
- 瘦身：代码混淆（R8/ProGuard）、资源压缩（shrinkResources）、so 按 ABI 拆分、移除无用资源、资源转 webp

**我的项目案例**
渠道 SDK 模块**编译期按需引入、运行期按线上配置启停**；登录渠道按 App/市场裁剪（合规 + 包体）。

**可能的追问**
- "R8 和 ProGuard 区别？" → R8 是 ProGuard 的替代，集成 shrinking + 优化 + 混淆，速度更快

### 17. 数据存储（MMKV / 数据库）

**踩分点**
- SharedPreferences：XML 全量加载、apply 异步 / commit 同步、线程安全但跨进程不安全
- MMKV：mmap + protobuf 序列化，效率高、支持跨进程
- 数据库：SQLite / Room，事务、索引、升级迁移
- 数据一致性

**我的项目案例**
麦位高频请求加缓存，减少无效流量与卡顿（缓存策略见 5.2）。

**可能的追问**
- "apply 和 commit 区别？" → apply 异步写内存 + 异步落盘，无返回值；commit 同步落盘返回结果

### 18. AI Coding 应用（热点题）

**踩分点**
- 工作流：需求 AI 出计划 → 基于 Skill 生成代码 → Bug AI 辅助定位
- 约束 AI：结构化 Skill / Rules / Context 注入，让生成代码遵循团队架构
- 局限：AI 无法稳定遵循复杂架构约束，需人工关键点 Review
- 工具：Copilot / Cursor / OpenCode

**我的项目案例**
把 HAGO 核心架构规范转化为结构化 AI Skill，约束生成代码遵循 MVVM、Service Manager、单向数据流；20 人团队日常使用，Review 返工率降低，交付效率提升约 30%；Vibe Coding 验证（2 周 4 款小游戏）发现部分架构约束 AI 无法稳定遵循，收敛为人工关键点 Review。

**可能的追问**
- "哪些约束 AI 学不会？" → **需要准备 1~2 个具体例子**（如跨模块通信的编译期校验、生命周期绑定等复杂隐式约束）
